# Requirement ระบบ Auto Reconcile Bank — Phase II ฝั่ง AP (เงินจ่าย)

> **ร่าง** — เขียนขึ้นจากระบบที่พัฒนาไปแล้ว (ฝั่ง AP ถูกทำคู่ไปกับ AR ใน Phase I)
> เอกสารนี้จึงมี 2 หน้าที่: (1) ให้ฝ่ายบัญชีเจ้าหนี้ **ยืนยัน** ว่าสิ่งที่ทำไปแล้วตรงกับที่ต้องการ
> (2) เก็บ requirement เฉพาะส่วนที่ **ยังไม่มี** ในระบบ เพื่อกำหนด scope ของ Phase II
>
> **สถานะกำกับแต่ละข้อ**
> - ✅ มีในระบบแล้ว — ต้องการแค่คำยืนยันจากผู้ใช้
> - 🟡 มีบางส่วน — ต้องตัดสินใจเพิ่มว่าจะทำต่อถึงไหน
> - 🔴 ยังไม่มี — ต้องเก็บ requirement ใหม่

---

## A. ภาพรวมและขอบเขตของ Phase II

1. ✅ ระบบเดิมกระทบยอด Bank Statement กับ BC365 ได้**ทั้งเงินเข้าและเงินออก**อยู่แล้ว โดยนิยามว่า **AR = เงินเข้า (IN)** และ **AP = เงินออก (OUT)** ใช้นิยามเดียวกันทุกหน้าจอ
2. ✅ ฝั่ง AP **ไม่ได้แยกเป็นระบบใหม่** — ใช้ฐานข้อมูล หน้าจอ และกติกาชุดเดียวกับ AR แค่สลับทิศทางเงิน
3. ❓ ต้องยืนยันว่า Phase II หมายถึง **"ทำให้ฝั่งจ่ายใช้งานได้จริงเต็มรูปแบบ"** (เติมของที่ขาด + UAT กับทีมเจ้าหนี้) ไม่ใช่การสร้างระบบใหม่ซ้ำ — ถ้าตกลงตามนี้ scope จะเล็กลงมากและควรแก้ชื่อ Epic ให้ตรง
4. 🔴 ต้องกำหนดว่า Phase II ครอบคลุม **บัญชีจ่ายกี่บัญชี ธนาคารอะไรบ้าง** และต้องย้อนหลังตั้งแต่งวดไหน

---

## B. แหล่งข้อมูลฝั่งจ่าย

5. ✅ ฝั่งบัญชีดึงจากตารางเดียวกับ AR คือ `BankAccountLedgerEntries` ที่ sync มาจาก BC365 ซึ่งมีรายการ **ทั้ง Debit และ Credit** อยู่แล้ว — ยอดสุทธิใช้สูตร `Debit − Credit` ติดลบคือเงินออก
6. ✅ ฝั่งธนาคาร parser ทั้ง 3 ธนาคาร (KBANK / SCB / BBL) อ่านช่อง **Debit (เงินออก)** และเก็บ **เลขที่เช็ค (chequeNo)** ไว้ให้แล้วตั้งแต่ตอนนำเข้า
7. 🔴 **ข้อที่ต้องเคลียร์ให้ได้ก่อนอย่างอื่น** — ในตาราง GL มี `Bank_Account_No` ที่ไม่ใช่บัญชีธนาคารปนอยู่ เช่น `PDC - R` และ `TRANSFER` ซึ่งตอนนี้ถูก JOIN กับ `BankAccountMapping` **ตัดทิ้งทั้งหมด**
   - ฝั่งจ่ายมีคู่แฝด (เช่น `PDC - P` หรือบัญชีพักเช็คจ่าย) หรือไม่
   - ถ้ามี — การตัดทิ้งแบบปัจจุบัน **ทำให้ยอดฝั่ง AP หายไปหรือเปล่า** ต้องพิสูจน์กับข้อมูลจริงก่อนตกลง scope
8. 🔴 ต้องยืนยันว่าข้อมูลที่ AP ต้องใช้อยู่ใน `BankAccountLedgerEntries` ครบหรือไม่ หรือต้องให้ทีม TRW Data Center เพิ่ม sync endpoint ใหม่ (เช่น Check Ledger Entry / Vendor Ledger Entry) — ปัจจุบันมีแค่ `/sync/BankAccountLedgerEntries` และ `/sync/BankAccountLedgerEntriesUpdate40days`
9. ✅ ฝั่ง GL ยังคง **ห้ามแก้ในโปรแกรมนี้** ผิดต้องไปแก้ที่ BC365 แล้วซิงค์ใหม่ (กติกาเดียวกับ AR)

---

## C. หน้าจอกระทบยอด (Reconcile) ฝั่งจ่าย

10. ✅ หน้า Reconcile มี **แท็บ "เงินเข้า / เงินออก"** แยกกัน เลือกดูทีละทิศได้
11. ✅ รายการที่ติ๊กค้างไว้ **ไม่หายเมื่อสลับแท็บ** และการกด "เลือกทั้งหมด" ในแท็บหนึ่ง **จะไม่ไปแตะรายการของอีกแท็บ** — ออกแบบมาเพราะ **เงินเข้ากับเงินออกมักเป็นคนละคนรับผิดชอบ**
12. ❓ ต้องยืนยันกับทีมเจ้าหนี้ว่าข้อ 11 ตรงกับวิธีทำงานจริงไหม — หรือคนเดียวกันดูทั้งสองฝั่ง
13. ✅ กติกาการจับคู่ใช้ชุดเดียวกับ AR: ทิศทางต้องตรงข้ามกัน, ยอดรวมสองฝั่งต้องเท่ากัน (ยอมต่างได้ไม่เกิน 0.005 บาท), รองรับ 1:1 / 1:N / N:1
14. ✅ มี **ผู้ช่วยหาคู่** สำหรับคู่ที่ยอดตรงกันแต่ลงคนละวัน (หน้าต่างค้นหา 3 / 7 / 15 / 30 วัน) และใช้ได้กับฝั่งเงินออกด้วย
15. ✅ คู่ที่ระบบแนะนำ **ต้องให้คนกดยืนยันเองเสมอ** ระบบไม่บันทึกให้อัตโนมัติ
16. 🟡 หน้า Reconcile **ยังไม่มี infinite scroll** (ตั้งใจให้เห็นชุดข้อมูลครบเพื่อจับคู่) — ถ้าฝั่งจ่ายมีรายการต่องวดเยอะกว่าฝั่งรับมาก ต้องประเมินใหม่ว่าจอจะอืดไหม

---

## D. เช็คสั่งจ่าย (ประเด็นใหญ่ที่สุดของ AP)

17. 🟡 ระบบ **เก็บเลขที่เช็คจากไฟล์ธนาคารไว้แล้ว** แต่ **ผู้ช่วยหาคู่ไม่ได้ใช้เลขที่เช็คให้คะแนน** เพราะพิสูจน์กับข้อมูลจริงฝั่งรับแล้วว่าใช้ไม่ได้
    - 🔴 ต้องพิสูจน์ซ้ำกับข้อมูล **ฝั่งจ่าย** ว่าเลขเช็คในไฟล์ธนาคารตรงกับเลขใน BC365 แบบเทียบตัวอักษรได้เลยหรือไม่ ถ้าได้ ควรเพิ่มเป็นเกณฑ์ให้คะแนน
18. 🔴 **เช็คที่ออกแล้วยังไม่ขึ้นเงิน (เช็คค้างจ่าย)** — ปัจจุบันระบบมองว่าเป็นแค่ "ยังไม่จับคู่" หรือให้ผู้ใช้กด "พักไว้" เอง ยังไม่มีสถานะเฉพาะ ต้องเก็บ requirement ว่า
    - ออกเช็คเดือนละกี่ใบ ค้างขึ้นเงินนานสุดกี่วัน
    - ต้องการสถานะแยกต่างหาก (เช่น "รอขึ้นเงิน") หรือใช้ Suspense เดิมพอ — ต่างกันตรงที่เช็คค้างขึ้นเงิน **ไม่ใช่ความผิดพลาด** แต่ aging ปัจจุบันตีความว่าเป็นรายการมีปัญหา
    - เช็คหมดอายุ (เกิน 6 เดือน) / เช็คยกเลิก / stop payment ต้องทำอย่างไรในระบบ
19. 🔴 ช่วงเวลาที่ต่างกันของฝั่งจ่ายอาจกินเป็นเดือน ซึ่ง **เกินหน้าต่างสูงสุด 31 วันของผู้ช่วยหาคู่** — ต้องตัดสินใจว่าจะขยายหน้าต่าง หรือทำกลไกแยกสำหรับเช็คค้าง

---

## E. การจ่ายรวมก้อน

20. 🔴 ต้องเก็บ requirement ว่ามีการจ่ายแบบ **media clearing / payroll / bulk transfer** หรือไม่ — ธนาคารตัดยอดรวมบรรทัดเดียว แต่ BC365 ลงหลายบรรทัด
21. ✅ ระบบรองรับ N:1 อยู่แล้ว (ธนาคารหลายรายการต่อ GL รายการเดียว) และ 1:N
22. 🔴 ถ้าก้อนหนึ่งมีหลายร้อยบรรทัด ต้องถามว่าธนาคารมี **ไฟล์รายละเอียดแนบ** ให้ไหม และผู้ใช้ยอมไล่ติ๊กเองหรือต้องมีตัวช่วยจับกลุ่ม

---

## F. ผลต่างและรายการปรับปรุง

23. ✅ ระบบรองรับ **การจับคู่ที่ยอดสองฝั่งไม่เท่ากันพอดี** โดยให้ใส่หมายเหตุกำกับ (ตกลงกันในการประชุมพิสูจน์ยอด 17 ก.ย. 2026)
24. ✅ รองรับ **รายการหักล้างกันเองฝั่ง BC365** (OFFSET) และ **JV ปรับปรุงพักโอน** (EXCLUDED) ซึ่งไม่มีคู่ฝั่งธนาคาร
25. 🔴 ต้องเก็บ requirement ผลต่างเฉพาะของ AP ที่ยังไม่ได้คุย
    - **ค่าธรรมเนียมธนาคาร / ค่าธรรมเนียมเช็ค** — ธนาคารตัดแยกบรรทัด แต่บัญชีลงรวมหรือแยก
    - **ภาษีหัก ณ ที่จ่าย (WHT)** — กระทบยอดเงินที่จ่ายจริงกับยอดตั้งหนี้อย่างไร
    - **จ่ายต่างประเทศ (TT)** — มีไหม ผลต่างอัตราแลกเปลี่ยนจัดการอย่างไร
26. 🔴 ต้องกำหนดว่า **ผลต่างเท่าไรถึงยอมให้ผ่าน** สำหรับฝั่งจ่าย (ของเดิม 0.005 บาท ไว้กันปัดเศษเท่านั้น)

---

## G. รายการค้าง / พักไว้ ฝั่งจ่าย

27. ✅ หน้า Suspense ใช้ร่วมกันทั้งสองฝั่ง มีตัวกรอง, aging badge, เลือกหลายรายการแล้วดึงกลับพร้อมกัน พร้อมกล่องยืนยัน
28. ✅ กติกาเดิมยังบังคับอยู่: **พักได้เฉพาะฝั่ง BC365 เท่านั้น ฝั่ง Bank Statement ห้ามพัก** เพราะเป็นเอกสารจากธนาคาร
29. 🟡 หน้า Suspense **ยังไม่มีตัวกรองแยก AR / AP** (ต่างจาก Reports / Dashboard / Match History ที่มีแล้ว) — ถ้าคนละทีมดูแล ควรเพิ่ม
30. 🔴 ถ้าตกลงตามข้อ 18 ว่าเช็คค้างจ่ายต้องมีสถานะของตัวเอง ต้องออกแบบว่ามันอยู่บนหน้า Suspense เดิมหรือแยกหน้าใหม่

---

## H. รายงานฝั่ง AP

31. ✅ หน้า Reports มี **ตัวเลือกฝั่ง AR / AP** แล้ว และ Excel ที่ export ออกมาระบุหัวรายงานว่า "AP — เงินออก"
32. ✅ รายงานแสดงครบทุกสถานะ: จับคู่แล้ว / ยังไม่จับคู่ / พักไว้ / หักล้างกันเอง / JV ปรับปรุงพักโอน
33. 🔴 **รายงานเช็คค้างจ่ายแยกตามอายุ** — ยังไม่มี ต้องเก็บรูปแบบที่ผู้ใช้ต้องการ (แยกตามอายุกี่ช่วง ต้องมีชื่อผู้รับเงินไหม)
34. 🔴 **Bank Reconciliation Statement มาตรฐาน** (ยอดตาม statement ± เช็คค้างจ่าย ± เงินฝากระหว่างทาง = ยอดตามบัญชี) — ยังไม่มีเป็นหน้ารายงานเดี่ยว ต้องถามว่าผู้สอบบัญชีขอแบบนี้หรือไม่
35. ✅ ตัวเลขในรายงานต้องตรงกับที่เคยทำมือ 100% — เกณฑ์เดิมของ Phase I ยังใช้กับฝั่งจ่าย

## I. Dashboard และประวัติการจับคู่

36. ✅ Dashboard เลือกมุมมองได้ **AR / AP / ทั้งสองฝั่ง** และนับรายการแยกฝั่งให้แล้ว
37. ✅ หน้า Match History มีแท็บกรอง **"AP · เงินออก"** และแสดงรายการสองฝั่งในตารางเดียว
38. ✅ ยกเลิกการจับคู่ได้ทั้งใบและเฉพาะกลุ่มย่อย พร้อมเก็บประวัติว่าใครทำเมื่อไร
39. ❓ ต้องยืนยันว่า KPI บน Dashboard ที่ทีมเจ้าหนี้อยากเห็น เหมือนกับที่ทีมลูกหนี้ใช้อยู่หรือไม่

---

## J. สิทธิ์และการแบ่งงาน

40. ✅ ระบบแบ่งสิทธิ์เป็น Admin / User / Dev และจำกัดหน้า Reconcile / Match History / Suspense ไว้ที่ Admin/Dev
41. 🔴 ต้องถามว่าทีมเจ้าหนี้กับทีมลูกหนี้ **ต้องเห็นข้อมูลของกันและกันหรือไม่** — ถ้าไม่ ต้องเพิ่มการแยกสิทธิ์ตามฝั่ง (ตอนนี้ยังไม่มี ทุกคนที่เข้าได้เห็นทั้งสองฝั่ง)
42. 🔴 ต้องระบุชื่อผู้ใช้จริงฝั่ง AP ที่จะเข้าร่วม UAT

## L. สรุปขอบเขตที่คาดว่าจะเป็นของ Phase II

**ของที่มีแล้ว ใช้ซ้ำได้ทันที** — โครงสร้างฐานข้อมูล, parser 3 ธนาคาร, GL sync, หน้า Reconcile แท็บเงินออก, ผู้ช่วยหาคู่, Suspense, Match History, Reports/Dashboard ฝั่ง AP

**งานที่น่าจะต้องทำจริงใน Phase II**
1. ตรวจ/แก้ขอบเขตบัญชีฝั่งจ่ายใน `BankAccountMapping` (ข้อ 7)
2. สถานะเช็คค้างจ่าย + aging เฉพาะทาง (ข้อ 18, 30)
3. จับคู่ด้วยเลขที่เช็ค ถ้าข้อมูลจริงรองรับ (ข้อ 17)
4. กติกาผลต่างเฉพาะ AP — ค่าธรรมเนียม / WHT / FX (ข้อ 25)
5. รายงานเช็คค้างจ่าย + Bank Reconciliation Statement (ข้อ 33, 34)
6. ตัวกรอง AR/AP บนหน้า Suspense และการแยกสิทธิ์ตามทีม (ข้อ 29, 41)
7. UAT กับทีมเจ้าหนี้ด้วยข้อมูลจริง
